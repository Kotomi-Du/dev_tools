Environment: Windows x64, Python env C:\Users\yarudu\Documents\pyenv\py311, windowsml 2.9.36a0 + windowsml-llama-core 2.9.36a0, repo WindowsML. GPUs: Intel Arc B580 and Intel UHD 770.

  • C++ app vs Python app: on the same Windows ML llama.cpp DLLs and Vulkan backend, the C++ app is 23× faster on the B580, 7× on the UHD 770 and 1.3× on CPU.
  • C++ app vs native: the C++ app reaches 77% of native llama-bench on the B580, 93% on the UHD 770 and 74% on CPU. Windows ML's llama.cpp build is therefore close to native; the gap comes from the path an app takes.
  • Not a cold start: the Python app stays slow on GPU in every run (1.7 s to the first token each time), while the C++ app is only slow on its first, cold run. The cost is in the Windows ML Runtime API path the Python app uses: the decoder pipeline stage, plus copying the logits to a CPU tensor, argmax and detokenizing in Python for each token. That overhead grows on GPU, where every step also waits for a GPU-to-CPU copy.
  • Recommendation: for GGUF on a dGPU, call llama.cpp's API directly through Windows ML's DLLs (llama-upstream-api), or investigate the per-token overhead of the Runtime API's llama stage.
  • Windows ML's Runtime API also exposes fewer tuning options (no -ngl, tensor overrides or flash attention; see section 4). The C++ route can set them.

1. How the stack fits together

python main.py --backend llama
  -> windowsml.runtime (ctypes)
     -> windowsml\lib\WinMLRuntimeCore.dll        (Runtime C/COM API)
        -> WinMLRuntimeLlama.dll                 (Windows ML adapter, closed source)
           -> WinMLllama.dll -> WinMLggml.dll -> WinMLggml-base.dll   (renamed llama.cpp core)
              -> LlamaBackends\cpu\ggml-cpu.dll        (shipped)
              -> LlamaBackends\vulkan\ggml-vulkan.dll  (built by us)
  • Every DLL is loaded by full path from site-packages\windowsml\lib, and os.add_dll_directory covers their dependencies. Nothing comes from PATH.
  • When the package loads, _llama.py checks size and SHA-256 against WinMLLlamaPythonPairing.json.
  • The core DLLs (WinMLRuntimeLlama, WinMLllama, WinMLggml*) are prebuilt by Microsoft and can't be rebuilt. Only ggml-<family>.dll backends can be built.
  • Default model: Samples\Runtime\models\gguf\qwen2.5-0.5b-instruct-q4_k_m.gguf.
  • Installed core: llama.cpp build 11847, commit 9145ddb9556c1cfa568f3189eb7be44317826e31, backend API 3, ABI 7, hybrid-crt.

2. Build the Vulkan backend

Prerequisites

  • Visual Studio 2022 with the v143 x64 tools, plus Git and CMake.
  • Vulkan SDK (here C:\VulkanSDK\1.4.363.1, with glslc).
  • LongPathsEnabled=1.
  • PowerShell 7. winget wasn't available and dotnet tool install PowerShell failed on SDK 8.0.400, so I installed the portable zip from GitHub releases into %LOCALAPPDATA%\pwsh7.
  • A Microsoft.Windows.AI.MachineLearning.LibLlama.Core .nupkg. No 2.9.36 version is on nuget.org. I used 0.7.0.113-experimental. It has the same llama.cpp commit, backend API and ABI as the installed core, but different DLL hashes.
    • Microsoft.Windows.AI.MachineLearning.LibLlama.Core 0.7.0.113-experimental, the package used for the build
    • Microsoft.Windows.AI.MachineLearning 2.9.36-experimental, the main package (it has no llama.cpp DLLs, so it can't be used as -CorePackage)

Steps

  1. Download the Core package into Samples\Runtime\localpackages: 
    $id='microsoft.windows.ai.machinelearning.libllama.core'; $v='0.7.0.113-experimental'
Invoke-WebRequest "https://api.nuget.org/v3-flatcontainer/$id/$v/$id.$v.nupkg" -OutFile ".\Samples\Runtime\localpackages\$id.$v.nupkg"
  2. The script won't build into py311 because py311's core DLLs don't match the package's. Instead, extract the package's own x64 payload into a scratch output folder: 
    Add-Type -A System.IO.Compression.FileSystem
[IO.Compression.ZipFile]::ExtractToDirectory($pkg, "$env:TEMP\libllama-core-0.7.0.113")
Copy-Item "$env:TEMP\libllama-core-0.7.0.113\runtimes\win-x64\native" "$env:TEMP\vk-out" -Recurse
  3. Run the build script under pwsh 7 inside a VS 2022 x64 dev shell. Use a short -WorkRoot: 
    $vs='C:\Program Files\Microsoft Visual Studio\2022\Professional'
Import-Module "$vs\Common7\Tools\Microsoft.VisualStudio.DevShell.dll"
Enter-VsDevShell -VsInstallPath $vs -SkipAutomaticLocation -DevCmdArguments '-arch=x64 -host_arch=x64'

.\Tools\llama\Build-LlamaBackend.ps1 `
  -Backend vulkan `
  -WorkRoot C:\wl `
  -CMakeOption "-DVulkan_ROOT=$env:VULKAN_SDK" `
  -CorePackage $pkg `
  -ExpectedPackageSha256 (Get-FileHash $pkg).Hash `
  -OutputRoot "$env:TEMP\vk-out"

    With the default work root (%TEMP%\winml-llama-backend-interop\...), the nested vulkan-shaders-gen build failed with No CMAKE_C_COMPILER could be found (MSB8066). Changing it to -WorkRoot C:\wl fixed the build. The script deletes its build folder when it fails, so write its output to a log file to see the error.

  4. Output: $env:TEMP\vk-out\LlamaBackends\vulkan\ggml-vulkan.dll plus WinMLLlamaBackendManifest.json (family vulkan, build 11847, commit 9145ddb9, API 3, hybrid-crt).
  5. Install into py311: 
    Copy-Item "$env:TEMP\vk-out\LlamaBackends\vulkan" `
  C:\Users\yarudu\Documents\pyenv\py311\Lib\site-packages\windowsml\lib\LlamaBackends -Recurse -Force
    py311's core accepted it even though its DLL hashes differ from the 0.7.0.113 package.

4. What Windows ML llama.cpp is missing compared with native llama.cpp

Windows ML wraps llama.cpp as one pipeline stage. Its only tuning options (IWinMLLlamaStageOptions, Python stage.llama_options()) are: thread_count (-t), batch_thread_count (-tb), micro_batch_size (-ub), plus context capacity (-c).

Native llama.cppWindows ML llama.cpp
-ngl N partial GPU offloadMissing. The whole model runs on one target (CPU or GPU).
--cpu-moe, --n-cpu-moe, -ot / tensor buffer overrides (e.g. MoE experts on CPU)Missing.
-sm, -ts, -mg multi-GPU split and main GPU selectionMissing from the Windows ML Runtime API. A GPU can only be picked with the ggml env var GGML_VK_VISIBLE_DEVICES. Possible through the llama.cpp API (llama-upstream-api sample, see below): layer works, row isn't supported by Vulkan.
--device list of devicesOnly CPU, GPU or NPU (NPU is rejected for GGUF).
Sampling (--temp, --top-k, --top-p, --min-p, penalties, grammar)Not in the sample, which uses greedy argmax over logits. The Tasks API has its own text-generation config.
-fa flash attention, -ctk/-ctv KV-cache types, --no-kv-offloadNot exposed.
--mlock, --no-mmap, --numaNot exposed.
RoPE / YaRN scaling overrides, --override-kvNot exposed.
LoRA adapters (--lora), control vectorsNot exposed.
Tools: llama-server (OpenAI API), llama-bench, llama-quantize, llama-perplexityNot shipped. Only the runtime DLLs are.
Any backend: CUDA, Vulkan, SYCL, OpenCL, HIP, Metal…The CPU backend ships. CUDA comes as an opt-in package. Others, like Vulkan, have to be built with Build-LlamaBackend.ps1.
Rebuild the core or pick any llama.cpp commitNot possible. The core DLLs are prebuilt, renamed (WinML*), hash-pinned and tied to WinMLRuntimeCore.dll.
Speculative decoding with a draft modelSupported (SetDraftPredictorPath / Tasks speculative options).

Ways to get the missing features

  • Call the llama.cpp API through Windows ML's DLLs: Samples\Runtime\interop\llama-upstream-api links WinMLllama.lib/WinMLggml.lib. From C++ you can then set llama_model_params.n_gpu_layers and tensor_buft_overrides (for example \.ffn_(up|down|gate)_exps to CPU, which is what --cpu-moe does).
  • Use native llama.cpp: build or download llama-cli/llama-server with Vulkan and use every flag, for example llama-cli -m model.gguf -ngl 999 --cpu-moe -t 8. This bypasses Windows ML.

Through the llama.cpp API on Windows ML's DLLs (llama-upstream-api)

I extended Samples\Runtime\interop\llama-upstream-api\main.cpp with --split-mode none|layer|row, --tensor-split A,B,... and --main-gpu N, which set llama_model_params.split_mode, tensor_split and main_gpu. It builds against the pinned LibLlama.Core 0.7.0.113-experimental, with the Vulkan backend copied to LlamaBackends\vulkan.

cd Samples\Runtime
.\build.ps1 -Configuration Release -PackageOnly -Sample llama-upstream-api
Copy-Item $env:TEMP\vk-out\LlamaBackends\vulkan .\out\x64\Release\llama-upstream-api\LlamaBackends -Recurse -Force
.\out\x64\Release\llama-upstream-api\llama-upstream-api.exe --model .\models\gguf\granite-3.1-1b-a400m-instruct-Q3_K_L.gguf `
  --prompt "Reply with one short greeting." --max-tokens 32 --split-mode layer --tensor-split 3,1

Devices registered: CPU (i9-13900K), Vulkan0 (Arc B580), Vulkan1 (UHD 770).

OptionsResult
--split-mode none --main-gpu 0Works (B580 only): "Hello! How can I assist you today?"
--split-mode layer --tensor-split 3,1Works (layers about 3:1 across B580 and UHD 770): "Hello! How can I assist you today?". llama.cpp's default device list leaves out integrated GPUs when a discrete GPU is present, so the sample passes every GPU and iGPU in llama_model_params.devices when splitting. Without that, the "split" silently ran on the B580 alone.
--split-mode row --tensor-split 3,1Fails: device Vulkan0 does not support split buffers. Row split needs a backend with split buffers, such as CUDA.
  • Finding: the multi-GPU layer split that the Windows ML Runtime API lacks works when an application calls llama.cpp's own API on the same Windows ML llama.cpp DLLs. The same route could add n_gpu_layers and tensor_buft_overrides (MoE experts on CPU).

Multi-GPU performance through Windows ML's llama.cpp DLLs

Measured with the llama-upstream-api sample itself (Windows ML's WinMLllama.dll core with the Vulkan backend built in section 2). The sample now prints [tokens=N, first=Xs, throughput=Y/s]: first is the prompt decode plus the first token, and throughput covers the tokens after it. Default prompt (Explain in one sentence why the sky appears blue.), --max-tokens 64, greedy, 3 runs each (mean shown).

$o = '.\out\x64\Release\llama-upstream-api'
$m = '.\models\gguf\granite-3.1-1b-a400m-instruct-Q3_K_L.gguf'
$env:GGML_VK_VISIBLE_DEVICES='-1'; & "$o\llama-upstream-api.exe" --model $m --max-tokens 64 --split-mode none                  # CPU only
$env:GGML_VK_VISIBLE_DEVICES='0';  & "$o\llama-upstream-api.exe" --model $m --max-tokens 64 --split-mode none                  # B580 only
$env:GGML_VK_VISIBLE_DEVICES='1';  & "$o\llama-upstream-api.exe" --model $m --max-tokens 64 --split-mode none                  # UHD 770 only
Remove-Item Env:GGML_VK_VISIBLE_DEVICES
& "$o\llama-upstream-api.exe" --model $m --max-tokens 64 --split-mode layer --tensor-split 1,1                                    # both GPUs 1:1
& "$o\llama-upstream-api.exe" --model $m --max-tokens 64 --split-mode layer --tensor-split 3,1                                    # both GPUs 3:1

  • Finding: splitting one model across the two GPUs is slower than the B580 alone: 3.5× slower at 3:1 and 5.2× at 1:1, and slower than CPU only. With a layer split, each token runs the UHD 770's share of layers one after another with the B580's, and its hidden state is copied between the two GPUs. The UHD 770 runs about 9× slower than the B580, so its share dominates the time per token.
  • A multi-GPU split only pays off when the model doesn't fit on one GPU, or when the GPUs are similar in speed. This 0.7 GB model fits easily on the 12 GB B580.
  • Through Windows ML's own DLLs, the B580 runs at 378 tok/s, close to native llama.cpp. The low numbers from the Python hello-language-model sample (4.09 tok/s on the B580) therefore come from that sample's Python loop and cold start, not from Windows ML's llama.cpp build.
  • The UHD 770's first run took 3.9 s to the first token, likely while the driver compiled and cached its Vulkan shaders. Later runs were warm.
