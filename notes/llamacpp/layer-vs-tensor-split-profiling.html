Layer split vs tensor split: two-GPU decode profiling

1. Conclusions

Key takeaway: this model is too light per token for tensor split. The MoE activates only 8 of 512 experts, so a decode token reads only about 2.8–2.9 GB in total (~1.46 GB per GPU in layer split). At 608 GB/s that is only about 2.4 ms of data reads per GPU. The rest of each token is fixed per-kernel launch cost. Tensor split makes each kernel smaller, but there is almost no data-read time left to save: halving the matrices saves ~0.5 ms per GPU. Meanwhile it doubles the launches per GPU and adds 84 GPU-to-GPU syncs per token. For this model, layer split is the better choice. Tensor split pays off only when per-token data reads are large enough to outweigh launch and sync costs: dense or larger models, or larger batches.
  1. The main cost of tensor split is all-reduce synchronization latency. Each token needs about 84 all-reduces at about 234 µs each, which is roughly 60% of decode time. Bandwidth is not the limit: each all-reduce moves only 12–28 KiB.
  2. The second problem is work inflation. Each tensor-split GPU is busy about as long per token as both GPUs combined in layer split (12.6 ms vs 13.6 ms). Even with free communication, tensor split would reach only about 12.6–13.0 ms/token, against 15.8 ms for layer split.
    • Each GPU still runs the full set of ~830 kernels per token. Each kernel launch costs about 11 µs of fixed overhead, regardless of its size.
    • Per GPU per token, about 2.9 ms is reading data (kernel time) and about 9.7 ms is fixed launch overhead. Halving the matrices saves only about 0.5 ms.
    • The LM head (~295 MB) and the f32 MoE router (~308 MB) run in full on both GPUs.
    • The 84 sync points cut each GPU's work into 85 pieces. The GPU drains and restarts its pipeline between pieces.
  3. Layer split's single handoff is cheap. It costs about 0.4 ms per token of real transfer and wait. Its ~2.2 ms gap to GPU time is small next to the GPU work.
  4. Possible improvements for tensor split:
    • fewer reductions per token, by fusing or batching them;
    • a lower-latency path(on oneccl): direct peer-to-peer GPU memory instead of staging through host memory with semaphore hand-offs;
    • splitting the LM head and router instead of running them on both GPUs;

Layer split pays both GPUs' busy time in series, so its kernel and overhead times are doubled in wall time. Tensor split runs the GPUs in parallel, but each one pays the full dispatch overhead, plus ~18 ms of sync wait. Removing communication alone gives ~1.2× over layer split (15.8 → 12.7–13.0 ms). Larger gains also need fewer dispatches per GPU.

How the split was estimated: bytes come from kernel shapes and quantization bit widths. Kernel time is bytes ÷ the 608 GB/s peak, so it is a lower bound. Overhead is the rest of the measured busy time.

How each mode moves data between GPUs

  • Layer split: each GPU holds whole layers. Per decode token there is one handoff: GPU0 sends its 14 KiB output activation to GPU1.
  • Tensor split: each layer's weight matrices are divided between the GPUs. Each GPU computes a partial result, and an all-reduce sums the partials so both GPUs hold the full result before the next step. This happens 84 times per token (42 layers × 2: after attention and after the MoE block), carrying 12–28 KiB each time.

Why each GPU's work is cut into 85 pieces

After each all-reduce, the next kernel needs the summed result from both GPUs. So each GPU must submit the kernels recorded so far and signal a semaphore (a GPU sync flag). It then waits for the peer before starting the next group. 84 cut points give 85 pieces per GPU per token, which matches the 10,722 decode pieces ÷ (63 tokens × 2 GPUs) ≈ 85.1 measured.

Layer split runs each GPU's half as one long piece with one ~0.4 ms handoff. Tensor split alternates compute and sync 85 times: about 12.6 ms of compute plus 18 ms of sync per GPU, 30.7 ms wall time. Each piece still contains the full set of norm, matrix-vector, top-k and add kernels for its block, so each GPU runs ~830 kernels per token instead of ~415.

Method 3: counterfactual, all-reduce skipped (tensor split)

GGML_VK_COMM_SKIP=1 makes the all-reduce return immediately. The output is wrong, but the kernel work is unchanged. Decode improved from 32.7 to 13.0 ms/token. So the all-reduces cost about 19.7 ms per token (~60%), or about 234 µs each. That is per-operation sync latency, not bandwidth.

Method 5: why tensor split inflates per-GPU work

Source: decode blocks of the GGML_VK_PERF_LOGGER run in perf-op-tensor/. The logger serializes kernels, so only counts, shapes and ratios are used.

  • Same kernel count per GPU: 830 dispatches per GPU per token (see the table in section 1).
  • Split kernels barely get cheaper: q2_K mat-vec at k=3584 takes 38 / 55 / 71 µs for m = 512 / 1792 / 3072. That fits ~31 µs fixed + ~0.013 µs per row.
  • Replicated work (~28% of per-GPU logger time): hidden-size RMS norms, the 512-expert MoE router + top-k, the full LM head (q6_K m=100544), MULTI_ADD/GET_ROWS/sampling ops.
  • Fragmentation: 85 pieces per GPU per token, each ending in a submit plus a semaphore wait.

Tooling notes

  • GGML_VK_PERF_LOGGER=1 serializes every kernel (tensor decode fell to 3.1 tok/s). In layer mode it aborts at ggml-vulkan.cpp:14598.
  • A system HTTP proxy intercepts localhost requests, so benchmark clients must bypass it.
  • The profiling patches are on the profiling branch. GGML_VK_COMM_SKIP produces wrong output and is for profiling only.
